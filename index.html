macOS · /etc/ssl/cert.pem

Apple still ships two roots
that should not be trusted.

macOS keeps a separate OpenSSL bundle at /etc/ssl/cert.pem, used by curl, git, Python, Ruby, and anything else that reads a CA file instead of the Keychain. Two root CAs are still in it. This removes them — in one command, with a verified backup and a one-command undo. 

$ curl -fsSL https://surak.github.io/macos-root-ca-cleanup/fix.sh | bash

It asks for your sudo password and writes exactly one file. Read fix.sh first if you like — it is 263 lines, most of them checks.

Both are self-signed roots: the signature on each one was made by its own key. Nothing above them vouches for them — they are trusted because they are in the bundle, and for no other reason. One of them, AAA Certificate Services, still carries a SHA-1 self-signature from 2004.

Apple's answer: do it yourself

Two trust stores. Apple maintains one of them.

macOS does not have one list of trusted roots. It has two, and they are not the same list:

storerootsmaintained by Applewho trusts through it
SystemRootCertificates.keychain 158 yes — shipped and updated with the OS, and published in Apple's root certificate list Safari, Mail, App Store, anything that calls SecTrust — the Keychain
/etc/ssl/cert.pem 128 no — a vendored file, and its own first line says so curl, git, python3, ruby, perl, /usr/bin/openssl

The second file does not even pretend to be a copy of the first — 128 roots against 158. Its first line is still the version-control tag it arrived with:

$ head -1 /etc/ssl/cert.pem
# $OpenBSD: cert.pem,v 1.22.2.1 2021/09/30 18:28:20 deraadt Exp $

An OpenBSD revision from 30 September 2021, inside macOS 27. Whatever has changed in Apple's trust store since then — and a great deal has — did not necessarily reach this file.

Nothing Apple ships will edit it for you

Apple does provide trust tooling, and it is documented in man security: add-trusted-cert, remove-trusted-cert, verify-cert. All three operate on trust settings in a keychain. Running security remove-trusted-cert against either of these roots would change nothing for curl:

$ curl -v https://example.com 2>&1 | grep CA
*  CAfile: /etc/ssl/cert.pem
*  CApath: none

CApath: none — there is no second place to look. curl never asks the Keychain, so a root can be distrusted in the Keychain and still be trusted by curl, git and every Python script on the machine.

And the file is undocumented: no man page on macOS mentions it.

$ grep -rl 'etc/ssl/cert.pem' /usr/share/man
$

So "do it yourself" is not a rhetorical flourish — it is the operating model. No preference pane, no security subcommand, no OS update path exists that removes a root from this particular file on your behalf. Apple ships it, five of its own command-line tools read it, and who gets to decide what is in it is you. That is the entire justification for a script that edits it — and for the backup it keeps.

Worth saying plainly: as of macOS 27.0.1, both roots are still in Apple's 158-root Keychain, and security verify-cert still validates them. Apple has not withdrawn either one from anywhere. This page does not exist because the OS is about to break — it exists because the decision was left on the table.

/private/etc is where /etc really lives on macOS — same file. Node is the interesting exception, and the reason this page can be precise: it carries its own bundle, so it is unaffected either way. If you use Homebrew's toolchain, those binaries consult Homebrew's own store and this script does not touch them; to cover those, set SSL_CERT_FILE or fix Homebrew's cert.pem the same way.

what it does

  1. Checks the ground first. Confirms macOS, finds the bundle, works out how many certificates are in it.
  2. Identifies before deleting. Locates each block by its subject line, then compares the certificate's SHA-256 fingerprint to a pinned value. Same name but different certificate? It stops and writes nothing.
  3. Builds the new bundle in a temp directory — never in place — and validates the result: the count must drop by exactly the number of blocks removed, and OpenSSL must be able to parse every remaining certificate.
  4. Keeps the original at /etc/ssl/cert.pem.orig (only if that file does not already exist, so a good backup is never overwritten).
  5. Installs atomically. The new bundle is written beside the target and renamed into place, so an interrupted run cannot leave you with a half-written CA store. Then it re-runs the test.

check it yourself

The test command — both roots gone, everything else still there:

openssl crl2pkcs7 -nocrl -certfile /etc/ssl/cert.pem \
  | openssl pkcs7 -print_certs -noout \
  | grep -E 'emSign ECC Root CA - G3|AAA Certificate Services'

No output, exit code 1 — that is the good result. And the script has its own report:

undo

The original bundle is never deleted, only parked. This puts it back exactly as Apple shipped it:

$ curl -fsSL …/fix.sh | bash -s -- --revert

the raw commands

No taste for curl | bash, and no taste for this script either? These are the four lines it automates. Paste them one at a time. The first one alone is the undo.

[ -e /etc/ssl/cert.pem.orig ] || sudo cp -p /etc/ssl/cert.pem /etc/ssl/cert.pem.orig

t=$(mktemp) && awk -v s='=== /C=IN/OU=emSign PKI/O=eMudhra Technologies Limited/CN=emSign ECC Root CA - G3' '/^(===|###) /{skip=0} $0==s{skip=1} !skip' /etc/ssl/cert.pem > "$t" && [ -s "$t" ] && sudo install -m 0644 -o root -g wheel "$t" /etc/ssl/cert.pem; rm -f "$t"

t=$(mktemp) && awk -v s='=== /C=GB/ST=Greater Manchester/L=Salford/O=Comodo CA Limited/CN=AAA Certificate Services' '/^(===|###) /{skip=0} $0==s{skip=1} !skip' /etc/ssl/cert.pem > "$t" && [ -s "$t" ] && sudo install -m 0644 -o root -g wheel "$t" /etc/ssl/cert.pem; rm -f "$t"

openssl crl2pkcs7 -nocrl -certfile /etc/ssl/cert.pem | openssl pkcs7 -print_certs -noout | grep -E 'emSign ECC Root CA - G3|AAA Certificate Services'

One weakness, if you paste them by hand: [ -s "$t" ] only proves the file is not empty. If the subject line ever changes — Apple re-issues a bundle, a DN gets reordered — awk removes nothing, the file is still non-empty, and the install silently rewrites the bundle with identical contents. Harmless, but you get a success message for a no-op. The script fails loudly in that case instead.

what is verified, and what is not

This page would rather be precise than dramatic, so:

claimstatus
Both roots are present in Apple's /etc/ssl/cert.pemverified — 128-certificate bundle, both blocks located by subject and fingerprint
Removing them changes nothing elseverified — byte-identical to the hand-made bundle, all 126 remaining certificates still parse
Nothing breaksverified locally — curl + Python TLS against six major hosts
They are revokednot verifiable from the certificates — see below

Root CAs are essentially never revoked through their own CRL: a root cannot sign the list that condemns it, so distrust happens out of band, when a trust program drops the root from its store. The AAA CRL is current (Last Update: Oct 29 2026) and lists zero entries; the emSign root publishes no CRL or OCSP endpoint at all. Neither observation proves or disproves a revocation — the certs themselves cannot tell you. On macOS 27.0.1, security verify-cert still accepts both, and both are still present in the 158-root SystemRootCertificates.keychain — Apple has not withdrawn them, from either store.

So: treat the removal as a deliberate policy decision — these two roots, out of my bundle, on purpose — rather than as a cleanup of something the OS already knows is broken. It is reversible, which is the point of doing it this way. If you want the authority's side of the story, the sources worth reading are the CA's own incident reports, the CCADB record for each root, and the root-store policy of whichever trust program you care about.

requirements & risks

  • macOS. The bundle path and root:wheel ownership are Apple's; nothing here fits Linux.
  • sudo for one write to /etc/ssl/cert.pem. The script authenticates against the terminal, so curl | bash works without a password prompt hanging on the pipe.
  • If a service you use genuinely chains to one of these roots, it will start failing after the fix. That is the intended behaviour — and --revert is one command away.
  • macOS updates may restore the bundle. Re-run --verify after a major upgrade; the script is idempotent.
